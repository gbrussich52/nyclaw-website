Section 1

Identity and instruction files

The agent starts every session blank. A few short files give it the context a new hire would need.

Most agent runtimes load instruction files at the start of a session. Names vary by tool. The jobs these files do are the same. Keep them as four separate files so each stays short and has one purpose.

1

Identity and principles (often SOUL.md or AGENTS.md)

Who the agent is, how it writes, what it values, and the act/ask boundary. It answers: "If I can't reach my operator, what would they want me to do?" Give it a name; a named identity tends to keep tone steadier across sessions.

2

Who it serves (often USER.md)

The person or team: goals, working style, what they dislike, how they want bad news delivered. What a good chief of staff knows without being told.

3

Durable facts (often MEMORY.md)

Active projects, locked decisions, lessons learned, where things live. Curated, not a chat log.

4

Environment (often TOOLS.md)

Your actual setup: hosts, services, where credentials are stored and which accounts it may use. References only. Never the keys themselves.

Template · Act/ask block for the identity file
## When to act vs. ask

ACT (no approval needed):
- Repair broken implementations of agreed-upon systems
- Maintenance, config corrections, bug fixes
- Internal notes and memory updates

ASK FIRST:
- Anything sent to an outside person
- Spending money, or paid API use beyond set limits
- New decisions not previously discussed
- Deleting data or changing access

Prune as models improve. Stronger models need less instruction, not more. Every quarter, archive any instruction file, prompt or skill that nobody opened and that doesn't encode a real failure you learned from. A lean, current set beats a pile of stale playbooks.

Section 2

Memory tiers and daily notes

If you don't design memory, you don't have it.

TierWhat it holdsLifespan
SessionThe current conversationGone when the session ends
Daily notesOne short file per day: done, decided, pending, lessonsRecent days load at session start; older ones are searched on demand
DurableCurated facts and locked decisions, plus deeper project files loaded on demandUntil you prune them

Write it down now

There is no mental note in an agent system. The moment something worth keeping happens, write it to a file: an API quirk, a decision and its reason, a status change, a preference you learned. Not at the end of the day. Before moving on.

Compress, archive, delete

Memory files decay. Keep the always-loaded file small enough that the agent reads all of it every session; set a size limit and enforce it. When it grows past the limit, summarize old entries and move the full text to an archive. Move finished project detail to its own file. Delete what is resolved and will not matter again. Review monthly. Don't over-build: if the agent won't read a file, don't create it.

Template · Daily note
## [DATE]
### Done
- [item]
### Decided
- [item]: reason [brief]
### Pending / next
- [item]
### Lessons
- [item]
## Durable file sections
WHO I'M HELPING · ACTIVE PROJECTS (keep the list short) · LOCKED DECISIONS (not re-debated unless reopened) · WHERE THINGS LIVE (references, never secrets) · LESSONS LEARNED (dated, specific) · LAST UPDATED

Before ending a session on any project, write the state: what was tried, what worked, what didn't, what's next. Skip it and the next session starts over and re-debates settled questions.

Section 3

The two-layer watchdog

Cheap checks run all the time. Expensive reasoning runs only when there is something to decide.

Layer 1, process monitor. A small shell script or system service that checks whether long-running processes are alive and restarts them if they crash. No AI, no API cost.

Layer 2, intelligence. The model that reads results, handles odd cases and decides. It is called when there is something to decide, never as a heartbeat.

The restart-loop trap

Never put a single-shot AI command under a "restart if exited" monitor. A command such as claude --print answers once and exits normally. The monitor sees "process exited," restarts it, which makes another paid call, which exits, which triggers another restart. It repeats silently until the bill shows up. Use the monitor only for processes meant to stay running, and have it tell a clean exit from a crash.

Section 4

Scheduled job hygiene

A job that is scheduled but doing nothing gives false confidence.

Scheduled jobs (cron, launchd, cloud schedulers, assistant task schedulers) are where neglect builds up fastest. Jobs outlive the projects they served, call scripts that moved, or hit endpoints that changed. You think data is being collected. It isn't. You find out weeks later.

  • Every job has a comment: what it does, why, and when it was created
  • Every job writes a timestamp when it finishes successfully, and something checks that timestamp
  • Monthly: confirm each job's script exists and its output is used; remove anything with no recent success
  • When a project is paused or killed, remove its jobs in the same session
  • No placeholder jobs; schedule only when the script is ready and tested
  • Run it by hand and check the output before you schedule it; watch the first few scheduled runs
Section 5

Cost discipline and model choice

Cost is the number of calls times the size of each call. Shape both.

Cost

  • Use code, not a model, for anything that is math or fixed logic.
  • Bound every paid call. No uncapped loops. Set a spend cap and an alert with the provider.
  • Estimate cost per run and per month before scheduling anything that calls a paid API.
  • A long context repeated many times is the expensive case. Start a fresh session with a short written spec, or batch items into fewer calls.
  • Review billing monthly. Anything costing more than it returns gets cut.

Model choice

  • Use the cheapest model that does the job well. Small, fast models for lookups, file chores and status checks. Mid-tier for most writing and coding. The largest models for hard planning and review.
  • Don't run routine monitors on your most expensive model.
  • Upgrade when a specific job fails on the current model, not when a new leaderboard appears.
  • Test every external API with real data before building on it. Validate response content, not only the status code. Have a fallback, or at least an alert, for critical paths.
Section 6

Before you call an automation done

Checklist · Design, build, launch, maintain

Design

  • Does this need model reasoning, or is it logic? If logic, write code.
  • What happens when it fails? What does "completed" look like?
  • What does a run cost? Is there a cap?

Build

  • Every external call has error handling
  • Logs record start, end and exit status
  • Credentials come from environment variables or a secret store, never the code
  • Dependencies are written down: what breaks if a service goes down?

Launch

  • Run by hand; output confirmed at the real destination
  • First few scheduled runs watched
  • Off switch documented and tested

Maintain (monthly, plus a fuller review each quarter)

  • Last successful run confirmed for each job; dead jobs removed
  • Is anyone using the output? If not, remove it
  • Security pass: rate limits, input handling, access
  • Costs reviewed against what the job is worth
